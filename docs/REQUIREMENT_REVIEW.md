# DanceMirror 需求与原型评审

> 评审对象：`docs/PRD.md`、当前 H5 原型、产品工程文档，以及 `dancemirror_wireframes.html` 低保真线框。
> 评审目的：识别下一轮产品决策、UX 设计和研发实施前的阻塞项。
> 状态说明：第 7 节产品问题已于 2026-07-17 完成决策并写入 `docs/PRD.md` v0.4；本文件其余章节保留为当时的评审证据。

## 0. 评审结论摘要

当前产品方向基本成立：让舞蹈爱好者上传老师示范和自己的练习视频，获得能够定位到具体时间点的差异解释及练习建议。

评审时的 PRD 是 **AS-IS 现状文档**，当时尚不能直接指导下一轮设计和研发。产品经理现已完成关键决策，`docs/PRD.md` v0.4 已升级为目标版本需求；当前主要工作从“等待产品决策”转为“补齐技术方案、设计状态和代码实现”。

综合判断：

- 核心用户目标方向明确，但缺少经过确认的目标用户边界、首要成功标准和结果可信度标准。
- 功能覆盖了“视频对齐困难、难以发现差异、不知道如何练”三个核心问题。
- 业务页面范围已经明显小于旧线框，不算过大；但浏览器端逐帧分析、音频对齐、主体框选、外部模型配置和多维评分叠加后，**技术 MVP 仍然偏重**。
- 当前最大的产品风险是界面承诺与真实能力不一致，而不是缺少更多功能。
- 当前最大的 UX 风险是所有操作同时出现，但用户不知道必须先完成哪一步。
- 当前最大的研发风险是缺少唯一报告契约、正式状态机、移动端性能边界和明确的前后端阶段边界。

建议下一版 MVP 聚焦：

```text
添加两段视频
→ 完成对齐
→ 本地姿态分析
→ 查看具体差异与练习建议
→ 点击问题时间点回看
```

在上述闭环稳定前，不应重新加入旧线框中的登录、历史、自动多人识别、热力图、轨迹、独立评分页和个人中心。

## 1. 产品经理视角

### 1.1 核心用户目标

**结论：方向明确，成功标准不明确。**

PRD 已把价值目标描述为“理解哪里不同、为什么不同、下一次先练什么”，比“得到一个分数”更符合真实练舞场景。

仍存在以下缺口：

- 目标用户目前主要来自合理推断，没有明确优先舞种、练习时长、拍摄条件和设备档位。
- 没有定义一次有效复盘最少应回答哪些问题。
- 没有定义用户如何判断反馈可信，以及错误反馈应如何降级表达。
- 没有可验证的产品成功标准，例如“用户能否定位问题”“建议是否可执行”“是否愿意用新练习视频再次比对”。本评审不建议自行补造数值指标。

### 1.2 功能是否解决用户问题

**结论：核心功能方向正确，但部分能力只解决了界面问题，没有解决业务问题。**

已经有效覆盖：

- 双视频并列展示，减少人工来回切换。
- 音轨偏移帮助定位相同动作区间。
- 报告提供时间点、老师动作、用户动作和练习建议。
- 点击问题时间点可回到视频验证反馈。

尚未真正解决：

- 主体框选只保存 UI 矩形，没有限制姿态检测区域，却向用户承诺“只分析框内人物”。
- “逐帧”按钮按固定 `1/30` 秒移动，对非 30fps 视频不是真正的逐帧。
- “重新比对”只重新分析旧素材，不等于用户练完后上传新视频再次验证。
- 多维评分没有专业校准依据，不能证明分数能够帮助用户改进动作。

### 1.3 MVP 是否过大

**结论：页面范围合理，技术与配置范围偏大。**

适合保留在 MVP：

- 无登录单页 H5。
- 老师视频与用户视频输入。
- 自动对齐及手动偏移兜底。
- 浏览器端结构化差异分析。
- 页面内报告及问题时间点回看。

建议从普通用户 MVP 中移除或隐藏：

- Endpoint、Model、API Key 设置。
- 尚未真实生效的主体框选。
- 未经校准且可能压过建议内容的综合评分。
- 与报告闭环无直接关系的技术解释和英文模块标签。

### 1.4 页面和流程逻辑断层

当前虽是单页面，但存在明显的状态断层：

- 上传、音轨对齐、手动偏移和开始分析同时可见，未表达先后依赖。
- 分析按钮在前置条件未完成时仍可点击，错误只能在点击后发现。
- 自动对齐过程中仍可应用手动偏移或删除视频，异步结果可能覆盖新状态。
- 新分析开始时旧报告数据和问题时间点不完全清理，失败后可能留下陈旧状态。
- 报告底部的“重新比对”与用户理解的“再练一次”不是同一件事。
- 旧线框中的“上传—自动处理—必要时选人—对比—评分”与当前“上传—手动对齐—可选框选—分析—报告”不是同一条产品路径，不能混用。

## 2. UX 设计师视角

### 2.1 主任务是否突出

**结论：视觉上突出，交互顺序不突出。**

390px 等效移动端首屏中，双视频上传区和“开始逐帧比对”按钮具有足够视觉权重。老师视频与用户视频的角色区分也较清楚。

问题在于：

- “自动对齐音轨”“应用偏移”“开始逐帧比对”同时成为可操作动作，用户无法快速判断当前下一步。
- 设置齿轮进入 Endpoint、Model、Key 配置，抢占了普通用户不需要的注意力。
- “Frame Compare”“Audio Alignment”“AI Compare”等英文和技术词没有帮助用户完成任务。
- 主按钮文案强调系统技术过程，没有直接表达用户收益。

### 2.2 信息层级是否合理

**结论：上传层级合理，报告层级需要调整。**

上传区：

- 双视频在首屏直接出现，符合核心任务优先原则。
- 音轨偏移属于技术中间状态，目前占据较大固定面积。
- 手动偏移在正常用户尚未遇到失败前就展示，增加理解成本。

报告区：

- 当前先展示五个评分，再展示问题和建议，容易让用户把分数当成结果中心。
- 这与 PRD 和 AI Spec 中“解释差异比打分更重要”的原则冲突。
- 问题卡缺少“客观检测”与“AI 推断”的区分，也没有置信度或证据范围。
- `safetyNote` 存在于数据中但未展示。

推荐的信息顺序：

```text
一句话总结
→ 最优先修正的问题
→ 具体差异和回看时间点
→ 可执行练习计划
→ 次级评分或诊断详情
```

### 2.3 操作路径是否过长

**结论：步骤数量可接受，但用户决策数量偏多。**

当前完成一次分析通常需要：

1. 添加老师视频。
2. 添加用户视频。
3. 点击自动对齐，或理解并应用手动偏移。
4. 判断是否需要框选本人。
5. 点击开始分析。

问题不在五步本身，而在用户需要理解“音轨偏移、主体锁定、自动追踪”等系统概念。

建议：

- 两段视频加载完成后自动开始音轨检测，正常情况下不要求用户主动理解对齐。
- 仅在自动对齐失败或可信度不足时展开手动偏移。
- 主体框选只有在能够真实影响检测时才出现；否则从 MVP 移除。
- 分析 CTA 应根据前置状态禁用，并明确显示缺少的步骤。

### 2.4 状态、引导和反馈机制

当前已经存在：

- 两个视频空状态。
- 音轨 idle、working、ready、error。
- 分析阶段文案和 spinner。
- 页面级状态徽标。
- 报告问题时间点反馈。

仍缺少或不完整：

- 首次使用时对“两段视频分别是什么”的简短说明。
- 拍摄条件提示，例如全身入镜、机位固定、光线和遮挡。
- 只上传一段视频后的下一步引导。
- 文件读取和视频解码状态。
- 视频无音轨、格式不支持、时长不合适的就近错误提示。
- MediaPipe 或外部资源加载失败的恢复动作。
- 姿态识别质量较差、局部追踪丢失的反馈。
- 分析耗时预期、取消入口和输入锁定。
- 错误发生位置与错误提示位置的对应关系；当前不少错误统一显示在分析按钮下方。
- 弹层的焦点管理、键盘关闭、对话框语义和屏幕阅读提示。
- 本地处理、外部模型调用和本地数据残留说明。

## 3. 研发视角

### 3.1 数据字段

**结论：现状字段盘点较完整，正式契约仍不完整。**

PRD 已记录运行时状态、音轨数据、姿态帧、DTW 对齐结果和报告对象，这是良好的研发基础。

需要统一的部分：

- `AI_SPEC.md`、模型 prompt、本地报告对象和 UI 实际消费字段不一致。
- `mismatches` 数量是 1–3 条，但设计文档要求固定 3 条。
- `priority`、`safetyNote`、`scores`、`structuredAnalysis`、`pipeline` 等字段的必填性和展示规则不明确。
- 模型结果只执行 JSON 解析，没有运行时 schema 校验。
- `cropRect` 的坐标空间、视频缩放映射、旋转处理和是否进入检测管线没有正式定义。
- 视频输入缺少正式的 `duration/fps/codec/hasAudio/orientation` 约束。
- 音轨 `confidence/correlation` 的产品含义和低可信度阈值未定义。

### 3.2 页面与任务状态

**结论：PRD 记录了大量当前状态，但代码缺少唯一、可约束的状态机。**

建议在实施前建立最小状态模型：

```text
upload: empty | partial | ready | invalid
alignment: idle | working | ready | low_confidence | error
subject: unavailable | unlocked | selecting | locked
analysis: idle | validating | processing | success | error | cancelled
report: empty | ready | stale
```

需要补齐的状态：

- 文件选择取消。
- 视频元数据读取中和读取失败。
- 视频无音轨。
- 自动对齐低可信度，而不是只有成功或失败。
- 部分姿态帧丢失和整体质量不足。
- CDN/WASM/模型资源离线或超时。
- 页面切后台、视频自动播放受限和任务中断。
- 重分析开始、失败与旧报告恢复。
- localStorage 不可用或数据损坏。

### 3.3 实现成本和可行性

当前可行但需要限制：

- Web Audio 音轨对齐。
- MediaPipe 单人姿态提取。
- 本地指标计算和结构化报告。
- 问题时间点双视频定位。

成本或风险较高：

- 两段视频按 1× 速度顺序进行逐帧提取，等待时间至少受到两段视频时长影响；长视频在移动端还会产生内存和发热风险。
- 移动 Safari、低端 Android、后台切换和远程模型资源加载的稳定性尚未定义。
- 真正限制检测区域需要处理视频坐标、Canvas 坐标、黑边、缩放、旋转和设备像素比，不是只传一个矩形即可完成。
- 真正的逐帧控制需要读取或估计视频时间基准，固定 `1/30` 秒不能覆盖所有视频。
- 旧线框中的自动多人候选、人脸预推荐、持续人物 ID、视角校正、热力图和推测轨迹均属于独立算法能力，不应进入当前 MVP。

### 3.4 前后端责任边界

**结论：当前运行边界清楚，但文档阶段边界冲突。**

当前代码实际边界：

- 视频、音频、姿态和指标在浏览器处理。
- 当前没有业务后端。
- 可选 Gemini 调用由浏览器直接发起。
- 最新报告和 API 配置写入 localStorage。

文档冲突：

- `TECH_SPEC.md` 同时描述“当前纯前端”和未来 `/api/analysis` 接口，容易被误认为当前需要实现。
- 隐私章节又出现“后端只在用户确认后处理”，与当前纯前端不一致。
- `TASKS.md` 仍描述无 Key 使用 Mock、发送关键帧给模型，与当前本地 MediaPipe/DTW 路径不一致。
- API Key 明文保存在浏览器并进入请求 URL，不适合作为普通 C 端生产方案。

下一版技术需求应明确二选一：

- POC：仅本地报告，模型配置只存在于开发环境。
- 正式 C 端：模型请求经受控后端代理，客户端不暴露供应商 Endpoint 和用户 Key。

## 4. 必须修复的问题

以下问题会导致产品承诺失真、核心流程不可控、安全风险或研发无法按统一口径实现，应在下一轮高保真或功能开发前解决。

| 编号 | 问题 | 影响 | 必须达到的结果 |
|---|---|---|---|
| M01 | 主体框选承诺与能力不一致 | 用户被告知只分析框内本人，但实际仍检测完整画面 | 实现真实裁剪/区域检测，或移除框选及所有“锁定本人、只分析此人、自动追踪主体”文案 |
| M02 | 前置步骤没有形成受控流程 | 用户可在缺视频、未对齐时点击分析，也可在自动对齐中修改输入 | 用明确状态机控制按钮、输入和异步结果；过期任务不得回写当前页面 |
| M03 | 报告 schema 不统一 | 本地报告、模型报告、AI Spec、设计要求和 UI 字段可能互相不兼容 | 确定唯一 schema、必填/可选字段、问题条数规则、版本号和运行时校验 |
| M04 | 重分析可能保留旧报告状态 | 新分析失败后旧时间点可能仍可点击，用户无法判断结果属于哪次任务 | 定义分析开始、成功、失败时报告与时间点的清理或恢复规则 |
| M05 | 没有移动端处理边界 | 长视频可能带来不可接受的等待、内存、发热或浏览器崩溃 | 明确支持浏览器、视频格式、最大时长/大小及超时策略，并提供前置校验 |
| M06 | 核心错误缺少恢复路径 | 无音轨、格式不支持、无人、资源加载失败等状态只能显示通用错误 | 每个核心阻断错误提供就近原因和可执行 CTA：重试、手动偏移、重新选视频或查看拍摄建议 |
| M07 | API Key 方案不适合 C 端发布 | Key 明文持久化并进入 URL，且技术设置干扰普通用户 | 将设置明确限定为开发/POC，或改由受控后端调用；正式稿不得要求普通用户配置 Endpoint、Model、Key |
| M08 | “逐帧”命名与固定 1/30 秒不一致 | 非 30fps 视频无法保证进入相邻真实帧，损害核心功能可信度 | 实现帧感知步进，或把功能和文案改为明确的固定时间步进 |
| M09 | 前后端与版本文档互相冲突 | 研发无法判断当前是否要实现后端、Mock、关键帧模型或本地分析 | 统一 PRD、Tech Spec、AI Spec 和 Tasks 的当前版本边界，并把未来 API 单独标为非本期 |
| M10 | 产品验收缺少结果可信度边界 | 分数和原因可能被用户理解为专业结论 | 明确客观检测、算法推断和自然语言建议的展示边界；未经验证的评分不得作为主结论 |

## 5. 建议优化的问题

这些问题不会立即导致功能错误，但会显著影响首次成功率、理解成本和长期使用体验。

| 编号 | 建议 | 预期收益 |
|---|---|---|
| S01 | 两段视频加载后自动进入音轨检测；仅在失败或低可信度时显示手动偏移 | 减少技术决策和一次额外点击 |
| S02 | 分析 CTA 根据当前步骤显示“还需添加用户视频 / 正在对齐 / 可以开始分析”等状态 | 让单页流程具备清晰顺序 |
| S03 | 报告先展示最重要问题和训练建议，再展示折叠或次级评分 | 与用户目标及“不以打分为主”原则一致 |
| S04 | 增加首次使用的三条短提示：视频角色、拍摄要求、本地处理说明 | 降低输入质量问题和隐私疑虑 |
| S05 | 在单视频状态提供明确的“下一步添加另一段视频”反馈 | 减少空白等待和误操作 |
| S06 | 把错误提示放到对应模块内，而不是全部集中到分析按钮下方 | 用户能直接理解哪里出错、如何恢复 |
| S07 | 用用户语言替换 “Frame Compare / Audio Alignment / AI Compare / MediaPipe / DTW” 等技术词 | 降低 C 端理解负担 |
| S08 | 区分“重新分析当前视频”“替换我的视频再练一次”“全部重新选择” | 建立清楚的复练路径 |
| S09 | 增加弹层语义、焦点管理、键盘关闭和触控目标检查 | 提升可访问性和移动端稳定性 |
| S10 | 为分析进度提供阶段、预计耗时范围或已处理视频时长，并允许取消 | 降低长等待的不确定感 |

## 6. 可以暂缓的问题

以下能力与当前“验证一次 AI 复盘是否有价值”的目标关系较弱，或实现成本显著高于当前收益。

- 登录、注册、头像和账号体系。
- 首页、底部 Tab、个人中心和消息系统。
- 历史报告、成长曲线、周/月对比和跨设备同步。
- 自动多人检测、人物候选、人脸相似度预推荐和持续人物 ID。
- 视角校正、透视校正、自动剪辑和镜头重构。
- 热力图、推测性轨迹线和红绿动作判定。
- 独立评分页、历史平均和排行榜。
- 社区、课程、老师题库、会员和支付。
- 分享海报、下载报告和社交发布。

## 7. 产品经理决策结果

以下问题已经关闭，并已转换为 `docs/PRD.md` v0.4 的流程、数据规则和验收标准。

| 编号 | 决策结果 |
|---|---|
| 1 核心成功结果 | 用户看懂至少一个非常明显、自己能够感知的问题，并获得舞蹈老师式的易懂、可执行建议 |
| 2 老师视频 | 老师和用户视频均为必需，缺少任一视频不得分析 |
| 3 人物锁定 | MVP 必需；老师和用户两侧都要锁定真实目标人物 |
| 4 音轨对齐 | 两段视频就绪后自动执行并显示过程；失败后进入手动校准 |
| 5 报告问题 | 输出 1–3 条并按重要性排序；问题与共享时间轴差异区间一一对应 |
| 6 判断依据 | 默认隐藏，用户按需展开可解释依据摘要；不展示原始思维链、坐标或调试数据 |
| 7 评分 | 综合和四维评分从 MVP 移除 |
| 8 外部模型 | 使用受控后端单模型服务；服务端管理 Key、额度、超时、重试和任务状态；结构化报告兜底 |
| 9 视频范围 | 单文件最长 3 分钟、最大 500MB，支持 MP4/MOV；服务端转为 H.264 + AAC、最高 1080p/30fps |
| 10 处理中操作 | 允许替换或删除；用户确认后取消旧任务，旧结果不得回写 |
| 11 重新比对 | 不提供独立功能；用户通过替换视频后再次生成 |
| 12 数据保存 | H5 不提供历史；准备隐私说明和本次数据删除能力，未来小程序/App 再设计保存 |
| 13 旧线框 | 保留多人检测后的单目标选择、内部质量控制和追踪丢失区间；废弃多人报告、排名、自动编号和调试信息展示 |
| 14 验证指标 | 验证反馈精准和建议可执行，不使用复练意愿作为本阶段指标 |
